Methodology

I design systems that make AI-assisted work behave more like production infrastructure than an open-ended conversation. My work sits across systems architecture, protocol design, and execution governance — defining how models understand tasks, separate authority from data, isolate working context, use resources, manage consequence, verify outcomes, and respond to uncertainty.

Some systems become project-specific production architectures. Others operate across projects as portable methodologies for controlling how AI-assisted work is understood, built, judged, executed, and verified. The objective is consistent: turn model capability into bounded, inspectable, reliable work.

APEX governance · execution methodology active

Portable governance and execution methodology for AI-assisted work. APEX defines how models distinguish claimed state from observed reality, reason about consequence, bind authority to exact actions, challenge execution, adapt to available capability, and verify what actually happened.

Stack: governance · execution control · verification · risk
View case study →

Why I built it

While operating AI-assisted production systems, I kept encountering the same deeper problem: strong reasoning did not guarantee operational truth. A model could understand a task while still blurring planning with execution, requested state with observed state, authorization with capability, or confidence with evidence.

Architecture

APEX was built as a governance layer around that problem. It separates authority from data, distinguishes observed, verified, asserted, inferred, and unknown state, classifies actions by consequence, and governs meaningful work through UNDERSTAND → BUILD → JUDGE → AUTHORIZE → EXECUTE → VERIFY → RECONCILE.

Consequence Model R0 → R3 bounded
Operating Modes governance / methodology adaptive
Execution Cycle 7 stages verified

Deployment

APEX is used directly inside my own AI-assisted building environments as the governing methodology for meaningful work. It sits above individual projects rather than belonging to one production domain.

Tested against

  • fresh-context initialization
  • cross-model portability
  • host capability differences
  • unsupported governance environments
  • unknown consequential context
  • authorization boundaries
  • uncertain execution
  • verification and reconciliation

Iteration

The system is repeatedly revised through live use, portability testing, fresh-context testing, and attempts to break its assumptions. Failure modes discovered during use are folded back into the architecture rather than patched as isolated prompt fixes.

BUILDER SYSTEMS production runtime · isolation active

Production runtime methodology for carrying stable operating rules across AI-assisted projects while preventing temporary job data from becoming permanent authority. Built around current-job isolation, resource authority, output discipline, and contamination control.

Stack: production systems · context isolation · resource authority
View case study →

Why I built it

Running multiple AI-assisted production workflows exposed a recurring failure class: long conversations accumulated old assumptions, previous-job resources, temporary instructions, and behavioral drift. Starting fresh removed contamination but also removed useful production methodology.

Architecture

BUILDER SYSTEMS separates persistent production protocol from temporary job state. Each current job receives its own resource boundary, authority, and working context while the useful production methodology remains reusable.

Its central operating principle became: protocol persists. job data dies.

Context accumulated → isolated scoped
Resources assumed → classified authority
Job State persistent → disposable bounded

Deployment

Used across my own production environments where separate jobs, assets, instructions, and output requirements need to coexist without silently contaminating one another.

Tested against

  • fresh-chat deployment
  • new-job boundaries
  • stale instructions
  • unrelated supplied resources
  • output-mode drift
  • temporary job data attempting to persist

Iteration

BUILDER SYSTEMS has been rewritten through repeated production use. Its architecture grew from practical failures rather than a single theoretical specification.

SYSTEMS ARCHITECTURE methodology · architecture canonical

Architectural methodology for diagnosing AI-assisted production environments before implementation. Separates permanent system logic from temporary job state, defines component roles, classifies resource authority, and determines how independent systems should interact.

Stack: diagnosis · architecture · boundaries · handoffs
View case study →

Why I built it

Individual prompts were solving local problems without solving the architecture around them. As production environments became larger, a better prompt could not fix unclear component boundaries, mixed responsibilities, or undefined resource authority.

Architecture

SYSTEMS ARCHITECTURE starts before prompt compilation. It diagnoses the production environment, separates permanent protocol from temporary job material, defines one dominant purpose per system, and establishes handoffs between components.

Starting Point prompt → system architecture
Components mixed → bounded roles
Handoffs implicit → explicit flow

Deployment

Used as the design layer behind my production systems and project-specific AI environments. It determines what should exist before those decisions are compiled into executable instructions.

Tested against

  • temporary resources treated as permanent rules
  • monolithic prompt growth
  • unclear system handoffs
  • multiple output modes inside one system

PROTOCOL COMPILER architecture → execution active

Translation layer between system architecture and executable model instructions. Converts architectural decisions into portable master protocols with explicit output modes, resource authority, failure behavior, context isolation, and operational boundaries.

Why I built it

Architecture alone does not execute. I needed a reliable translation step between a system specification and the exact instructions a model would receive in a fresh environment.

Architecture

PROTOCOL COMPILER takes architectural decisions and converts them into executable master protocols. The compiled result locks the system's dominant purpose, defines allowed inputs and outputs, establishes resource authority, and specifies behavior when required information is missing or conflicting.

Input architecture structured
Compile protocol locked
Output executable portable

Deployment

Used to turn production architectures into canonical prompts that can be moved into fresh model environments without rebuilding the system manually each time.
